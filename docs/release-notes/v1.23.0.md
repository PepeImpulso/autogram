# v1.23.0 — Autogram is an Android assistant 🎙️🚗

Closes [issue #63](https://github.com/PepeImpulso/autogram/issues/63).
Promotes the assistant pre-release line (rc.1 → rc.9) to a stable
release. Autogram now appears in *Settings → Default digital
assistant app*, can be invoked from the Samsung gesture / side-key,
records the user's voice, sends it as a Telegram voice note to the
configured primary target (Merlín by default), and reads the
incoming reply aloud through the existing autoplay pipeline.

This release is the consolidated set of behavior + bug fixes from
rc.1 through rc.9 — **no new code lands at v1.23.0 vs. rc.9**, only
the version stamp and the GitHub release flag change.

## ✨ Added — Assistant role + voice loop

- **Phase 1 · Default-assistant role registration.**
  `AssistantActivity` declares `ACTION_ASSIST` and `VOICE_COMMAND`
  intent-filters so Autogram surfaces in *Settings → Default digital
  assistant app* on Samsung One UI alongside Google / Bixby /
  ChatGPT / Claude. Localized to all 6 UI locales
  (en/es/fr/de/zh/ja).

- **Phase 1b · `VoiceInteractionService` chain.** Listing the
  activity isn't enough — Samsung's long-press-home / side-key
  gesture binds through `VoiceInteractionService`, not the
  `ACTION_ASSIST` intent. `AutogramVoiceInteractionService` +
  `AutogramVoiceInteractionSessionService` +
  `AutogramVoiceInteractionSession` provide the OS bind point;
  on `onShow()` the session immediately launches `AssistantActivity`
  and dismisses itself. Manifest declares `BIND_VOICE_INTERACTION`
  (system-only permission so other apps can't impersonate us);
  `res/xml/assistant_metadata.xml` declares `supportsAssist=true` +
  `supportsLaunchVoiceAssistFromKeyguard=true` so the gesture works
  from the lock screen.

- **Phase 2 · Voice request → reply loop.** `AssistantViewModel`
  drives the state machine: `Idle → Listening → Transcribing →
  (ActionExecuted | Sending → WaitingForReply → Replied | Failed)`.
  60 s reply timeout. Reuses the existing `SendVoiceMtprotoUseCase`
  pipeline — zero new HTTP client, zero new DI modules. When the
  reply lands the activity dismisses; the existing
  `MtprotoReceiverService` + autoplay path reads the reply aloud.

- **Phase 5 starter · Contact picker.** A chip row at the top of
  `AssistantActivity` lets the user route the voice note to any
  pinned contact instead of always Merlín. Default selection is the
  configured primary target. Reuses v1.22.0's `ContactFilterRow`
  with a new `includeAllChip: Boolean = true` parameter — History /
  Pending keep their leading "All" chip; the assistant passes
  `false` since every assistant turn must resolve to a specific
  contact.

- **Phase 5 voice commands.** After the user stops recording,
  `AssistantCommandParser` runs the locally-transcribed text against
  Spanish + English keyword tables for `play pending`, `repeat
  last`, `pause`, `resume`, `stop`. On match: action executes,
  recording is discarded, brief confirmation, activity closes.
  Otherwise the recording falls through to the Phase 2 voice-note
  send. Tightened precision over recall — false-positives silently
  drop the recording rather than swallowing a real voice message.

## 🐛 Fixed — Quality-of-life on the playback path

- **rc.6 · Tap-to-seek + live timer + 2 s drain delay.** Pending
  Queue's *Now Playing* waveform is interactive (tap to jump, drag
  to scrub); AA's progress bar / lock-screen scrubber wired through
  `ACTION_SEEK_TO` + `MediaSessionCompat.Callback.onSeekTo`;
  `PlayReplyUseCase.seekTo()` re-publishes the position to the
  session synchronously so AA doesn't briefly snap back. History +
  Pending row gets a live `0:15 / 1:30` readout when active.
  `drainPendingIfAutoPlay` now waits 2 s after the mic releases
  before draining, and re-evaluates its guards (recording started
  again? autoplay toggled off?) before firing — no more queued
  audio stepping on the user's own context-switch right after
  `stopAndSend`.

- **rc.7 · Inline waveform on the active row.** The waveform that
  used to live only in the Pending Queue's *Now Playing* panel now
  also renders below the active row in History and Pending, with
  the same tap + drag-to-seek gestures. The `0:15 / 1:30` readout
  moved next to the arrival time so a 2-line subtitle no longer
  hides it. Polling state hoisted so the trailing time column and
  the inline waveform read the same numbers each frame.

- **rc.8 · Audit-driven race fixes.**
  - `AssistantViewModel.startReplyWatcher` reply / timeout race:
    `replyWatcher` and `timeoutJob` share `viewModelScope`'s Main
    dispatcher; the continuation after `.first()` had no suspension
    point before the `State.Replied` setter, so a queued timeout
    could flip state to `Failed` and the still-queued reply
    continuation could overwrite it back to `Replied`. Guarded
    with `if (_state.value is State.WaitingForReply)`.
  - `PlayReplyUseCase.seekTo` stale `playing` snapshot: the
    `_playbackStatus.value is Playing` check was read on the
    calling thread and carried into a `playbackScope.launch`, so
    a pause that landed between `audioPlayer.seekTo()` and the
    launch's body running could leave AA showing "playing at the
    new position" before the pause's own state push corrected it.
    Snapshot is now read inside the launch.

- **rc.9 · `pause()` now stops TTS too.** Pre-rc.9 `pause()` only
  called `audioPlayer.pause()`, which is a no-op when the active
  engine is `TtsPlayer` (text messages in History, or audio messages
  whose summary is read aloud because `summarizeLongMessages` is
  on). The button toggled to Play visually but the voice kept
  speaking. Now `pause()` checks `ttsPlayer.isSpeaking()` first and
  routes through a new `TtsPlayer.cancel()` that stops the engine
  WITHOUT firing the pending `onDone` (so the autoplay-drain
  `speak()` callbacks don't auto-advance the queue under the user
  — pause shouldn't auto-skip to the next message). `currentPlayingId`
  nulled, message marked `PLAYED` so it leaves the *Now Playing*
  panel, session flipped to `STOPPED`. A re-tap on Play starts a
  fresh utterance from the beginning — the only sensible "resume"
  for TTS, which Android `TextToSpeech` has no genuine pause/resume
  for.

## 🔍 Changed

- **rc.5 · Rebased on top of `v1.22.4`.** Pulled the v1.22.x master
  work (pulsing playback ring, AA voice search, headset routing)
  into the assistant branch. No assistant code change in rc.5 —
  pure rebase + smoke build.

## 📐 Architecture decisions

- **Backend: reuse Telegram MTProto.** No new HTTP client, no
  separate assistant API. The assistant turn rides the existing
  `SendVoiceMtprotoUseCase` pipeline. Closes Phase 3 from the
  original issue scope as N/A.
- **Persona: Merlín by default.** Resolved from the configured
  primary target. The contact picker overrides per-turn.
- **Recording: tap-to-stop, no VAD.** Hands-free voice activation
  detection was not in scope.
- **Reply UX: close + autoplay.** `AssistantActivity` dismisses
  when the reply lands; the existing `MtprotoReceiverService`
  autoplay path reads it. If the user backs out mid-turn, the
  reply still arrives via the receiver — no orphaned UI.

## 🚫 Out of scope (intentionally)

- **Phase 4 · Screen context capture.** Privacy-sensitive — would
  require explicit opt-in + clear UX. Deferred until requested.
- **Phase 5 voice-command full NLU.** "Send X to Y" parsing was
  ruled redundant given the contact picker already covers
  multi-target sending.
- **Always-listening / wake-word.** Out of scope for v1; the
  gesture / side-key trigger is sufficient for hands-free use.
