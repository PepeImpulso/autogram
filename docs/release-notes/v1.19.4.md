# v1.19.4 — Fifth audit: fix duplicate-send race introduced by v1.19.3 🔁

The fifth audit pass caught a real user-visible regression from
v1.19.3 — voice notes could be **delivered to Telegram twice** —
and reported no other real bugs across the rest of the codebase.

## 🐛 Fixed

### Duplicate voice-note delivery on fast consecutive sends

v1.19.3 changed the `RetryWorker` enqueue policy to
`ExistingWorkPolicy.REPLACE`, which cancels any running worker
before starting a fresh one. Intent: reset the backoff clock so
a new offline message doesn't wait up to 5 hours. Consequence:

1. User records a voice offline → `QUEUED_OFFLINE`.
2. Network returns → `OutboxRetryUseCase` flips the row to
   `SENDING` and calls `tdLibClient.send(SendMessage)`. The TDLib
   JNI upload starts in the background.
3. Before the upload finishes, the user records a SECOND voice.
   `SendVoiceMtprotoUseCase.persistQueuedOffline` calls
   `RetryWorker.enqueueOnce()` → `REPLACE` policy cancels the
   running worker mid-upload.
4. Cancelled coroutine throws at `deferred.await()`. But
   **TDLib's native upload does not respect coroutine cancellation**
   — it continues in background and eventually delivers voice
   #1 to Telegram.
5. Our row state for voice #1 stays in `SENDING` (coroutine
   cancelled before we could write `SENT`).
6. Next worker run: `resetStuckSending()` promotes the row back
   to `QUEUED_OFFLINE` → we re-send it → **voice #1 arrives in
   Telegram a second time**.

Trigger window: the 2-5s a voice note takes to upload. Users who
recorded back-to-back messages on shaky networks would have hit
this regularly.

Reverted the policy to **`APPEND_OR_REPLACE`** (what we had
pre-v1.19.2). Trade-offs documented inline in `RetryWorker.kt`:

- `APPEND_OR_REPLACE` never cancels a running worker — fresh
  work appends after it. No duplicate sends.
- The 5h stall that v1.19.2/.3 tried to fix is genuinely
  possible but much rarer than the duplicate-send race, and
  WorkManager's `NetworkType.CONNECTED` constraint restarts the
  worker immediately on reconnection, bypassing most of the
  backoff delay.

The `MessageDao.resetStuckSending()` introduced in v1.19.3 is
kept — it's still useful for process-kill scenarios where TDLib
died alongside our coroutine (no native upload continuing in
that case, so un-stucking the row is safe).

## 🧹 Stats page

No real bug here, just a note: v1.19.3's `getLifetimeStats()`
pattern remains correct. Stats are a one-shot snapshot; the user
can pull-to-refresh via the existing `StatsViewModel.refresh()`.

## 🧪 Cosmetic finding — not fixed

The 7-day chart uses a fixed 86,400,000 ms per day, which drifts
by ±1 hour on DST transition days. Totals stay correct; only
which of two adjacent bars a message near midnight is counted
under changes. Pure cosmetics — not worth the complexity of
calendar-arithmetic buckets.
