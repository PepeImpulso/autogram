# v1.19.1 — Second audit pass: 6 more real bugs 🧹

Re-ran the hostile audit against v1.19.0 (including the code I
added in that release). Found six issues worth shipping, four
of them genuine regressions or logic bugs. No user-visible
behaviour changes beyond the bugs going away.

## 🐛 Fixed

### 1. Cache-key operator precedence silently collided glyphs

`AutogramSurfaceRenderer.drawDrawableCentered` packs `(resId,
intSize, tint)` into a Long cache key. Kotlin parses

```kotlin
resId.toLong() and 0xFFFFF shl 44
```

as `a and (b shl c)`, not `(a and b) shl c` — both `and` and
`shl` are infix operators with the same precedence, applied
left-to-right. The old form masked `resId` with a pre-shifted
sentinel and dropped its low 20 bits. Different glyphs with
colliding high bits would share a cache entry and render with
the wrong tint or size. Fixed by parenthesising every
`and`-before-`shl`.

### 2. TTS ABA race: old utterance's listener fired new utterance's callback

`TtsPlayer.speak` replaces `pendingOnDone` on each call. The
engine's `OnUtteranceProgressListener` runs on a binder thread
and can deliver `onDone`/`onError` events for a stopped
utterance AFTER the next `speak()` has swapped in a fresh
callback — firing the NEW utterance's `onDone` at the OLD
utterance's tail event. Playback chain advanced prematurely;
occasionally the queue drained too fast. Fixed by tracking
`pendingUtteranceId` and ignoring listener events whose `id`
doesn't match.

### 3. `SendVoiceMtprotoUseCase.startRecording` didn't guard against pipeline-busy state

If the user tapped Record while `SendStatus` was `Validating`
or `Sending` (e.g. double-tap just after a previous
stop-and-send), `startRecording` only checked
`audioRecorder.isRecording()` — which returns false because
the recorder had already been released — so a brand-new
recording would start on top of the in-flight send,
overwriting `currentAudioFile` and flipping the UI out of
`Sending`. Added an explicit state gate: only `Idle`, `Sent`,
`Error`, `Discarded`, `QueuedOffline` admit a new recording.

### 4. Drawable raster cache grew unbounded

`ConcurrentHashMap<Long, Bitmap>` was never bounded. Shortcut
chip sizes depend on dynamic layout (surface dimensions, number
of visible shortcuts), so reconnections to different head
units or orientation changes produced new size buckets that
accumulated indefinitely. Replaced with a 24-entry
access-ordered `LinkedHashMap` in `Collections.synchronizedMap`,
and added a `drawableRasterCache.clear()` on
`onSurfaceDestroyed` so the cache doesn't survive a
resize/reconnect cycle.

### 5. Voice-shortcut save had a non-atomic rename window

`saveVoice` used `dst.delete() + staging.renameTo(dst)`. A
process kill between the two calls would leave the user with
the old shortcut deleted and no replacement. Replaced with
`Files.move(staging, dst, REPLACE_EXISTING, ATOMIC_MOVE)`,
which maps to POSIX `rename(2)` — atomic at the filesystem
level, so either the old file remains or the new one does,
never neither.

### 6. `stopAll` / utterance-id cleanup tidying

`TtsPlayer.stop()` and the `onFailure` branch of `speak()`
were clearing `pendingOnDone` but not `pendingUtteranceId`.
Harmless (the next `speak()` would clear it), but inconsistent.
Now cleared together.

## 🤷 Considered and not applied

- Scope-capture in `audioPlayer.play` callback. Auditor
  flagged that if `stopAll` cancels+recreates `playbackScope`
  during an in-flight callback, the `.launch` would run on
  a cancelled scope. On closer read: `playbackScope` is a
  `var` so lambda calls read the current (fresh) scope each
  invocation, AND `stopAll` already synchronously sets
  `_playbackStatus = Idle` + `currentPlayingId = null`, so
  state stays consistent whichever scope the callback
  eventually posts to. Kept the simpler code.
