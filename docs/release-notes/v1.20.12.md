# v1.20.12 — Pre-install audit fixes for the v1.20.11 UX rebuild

In-depth audit of the v1.20.11 pending-playback UX rebuild caught three
real bugs before the user exercised them. v1.20.12 ships v1.20.11 + the
audit fixes; users on the in-app updater will skip past v1.20.11.

## Fixed

- **Pending queue no longer "ghost-vanishes" after Stop / new recording.**
  `PlayReplyUseCase.stopAll()` used to clear the in-memory pending queue,
  but the `PendingPlaybackDao` rows survived — so `restorePendingQueue`
  re-loaded them on the next app launch and pending messages reappeared
  out of nowhere. With v1.20.11's new "▶ N pending" affordance making
  the queue a visible user-facing surface, that mismatch was about to
  become user-visible. `stopAll` now stops the current playback only;
  the queue stays put and the pending-replies notification is refreshed
  with the surviving count.
- **Tapping "▶ N pending" while another message was already playing no
  longer ghosts the first queued message.** `playAllPending` popped the
  first message and called `playVoiceMessage`, which then hit its
  "audio already playing" gate and re-enqueued the message at the END
  of the queue — but its DAO row had already been deleted, so the
  message was effectively orphaned and disappeared on the next app
  restart. `playAllPending` (and the new History `playFromHere` for
  symmetry) now hard-stops any in-flight playback before popping, so
  the queued message actually starts playing.
- **Per-incoming-message launcher badge no longer flips back to ON
  during a race.** Toggling Settings → Show pending badges to OFF
  triggers a delete + recreate of the notification channel (Android
  forbids mutating `setShowBadge` on an existing channel). If a new
  incoming-message notification posted in the microsecond window
  between the delete and the recreate, the channel was re-created
  with the default `setShowBadge=true` and the user's preference was
  silently reverted until the next app resume. The notifier now
  remembers the desired badge value as a `@Volatile` field and uses
  it on every `ensureChannel` call.
