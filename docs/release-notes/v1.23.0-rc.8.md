# v1.23.0-rc.8 — Audit-driven race fixes 🛠️

A debug sweep across the assistant + playback path after rc.7
surfaced two latent races. Both were narrow enough to slip under
manual testing but visible if you stared at the right state for
the right ~10 ms.

## 🐛 Fixed

- **Assistant · `AssistantViewModel.startReplyWatcher` reply / timeout
  race.** The `replyWatcher` and `timeoutJob` coroutines share
  `viewModelScope`'s Main dispatcher, but the continuation after
  `.first()` had no suspension point before the `State.Replied`
  setter. If the timeout queued first, the timeout flipped state to
  `Failed`, then the still-queued reply continuation overwrote it
  back to `Replied` — surfacing as the assistant briefly showing
  "No reply within 60s" and then auto-closing as if the reply had
  landed. Now guarded with `if (_state.value is State.WaitingForReply)`
  so the last writer no longer wins blindly. Same guard pattern the
  timeout side already used.

- **Playback · `PlayReplyUseCase.seekTo` stale `playing` snapshot.**
  The MediaSession push for AA / lock-screen was driven by a
  `_playbackStatus.value is Playing` snapshot read on the calling
  thread, then carried into a `playbackScope.launch { … }` block.
  If a pause landed between `AudioPlayer.seekTo()` (calling thread)
  and the launch's body running (playback dispatcher), AA briefly
  showed "playing at the new position" before the pause's own state
  push corrected it — exactly the one-frame jump rc.6 was trying to
  prevent. Snapshot is now read inside the launch, so the
  MediaSession push always reflects the live playback state at the
  moment AA / lock-screen sees it.

## 🔍 Changed

- **Assistant · drop unused `selectedTargetTitle()`.** The Idle
  screen reads its title from an inline `remember(selectedTargetId,
  availableContacts)` block now; the helper was orphaned in rc.2's
  contact-picker work.

## 🧪 Tests + verification

- `:app:assembleDebug` green.
- Six debug sweeps across assistant / playback / queue / parser /
  receiver / AA bridge — only these two real bugs surfaced; the
  rest of the agent findings were either speculative or already
  correctly handled (`withLock`'s implicit unlock on `return`,
  `audioPlayer.seekTo` already wrapping in `runCatching`,
  `MediaSession.release()` deliberately tied to process lifetime
  for AA reconnect, etc.).
- All v1.23.0-rc.7 verifications still apply (inline waveform,
  tap/drag-to-seek, live `0:15 / 1:30` readout, AA `ACTION_SEEK_TO`,
  pulsing playback ring, AA voice search, 2 s drain delay).
