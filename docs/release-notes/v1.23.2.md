# v1.23.2 — AA reply button + audio-routing hotfix 🚗🔊

Two on-device bugs Pepe reported after testing v1.23.1 in the car.

## 🐛 Fixed

- **AA · Reply button now appears on the heads-up notification.**
  Pre-v1.23.2 the notification posted by `IncomingMessageNotifier`
  carried `NotificationCompat.MessagingStyle` + a `RemoteInput`
  action with `SEMANTIC_ACTION_REPLY` + `setAllowGeneratedReplies(true)`
  — all the wiring AA needs — but `automotive_app_desc.xml` didn't
  declare `<uses name="notification" />`, so Gearhead didn't
  recognize Autogram as a messaging-class app and refused to
  surface the inline Reply control on the car screen. The pre-rc
  comment claimed adding this capability made Gearhead 16.5 launch
  its built-in empty messaging inbox instead of our template; that
  behavior didn't reproduce on modern Gearhead once `template` is
  declared first. Re-added the capability with the
  comment updated to record the real trade-off (a real
  `MessagingService` endpoint would be the right answer if a
  Gearhead version regresses; not dropping the declaration).

- **AA + Bluetooth · audio now reaches the car speakers without
  toggling Bluetooth off.** Pre-v1.23.2, when both USB AA and a
  Bluetooth pair to the same car were active, `AudioPlayer`'s
  `preferOutputRoute()` forced `setPreferredDevice(BT A2DP)` on
  the assumption that BT A2DP would carry audio to the car's
  audio system. Real-world finding (Galaxy + USB AA + BT pair to
  the same car): the car treats BT A2DP and USB AA media as
  separate sources and only renders one at a time. With USB AA
  active, BT A2DP is muted at the car — so the forced preference
  sent the audio to a silenced sink. The user reproduced this by
  having to disable phone Bluetooth to get audio out of the car
  speakers; toggling BT off removed BT A2DP from the device list,
  which made the picker return null, which skipped
  `setPreferredDevice`, which let the OS route through AA's media
  stream and the audio came through.

  Fix: when an AA sink is present, leave routing entirely to the
  OS. The `MediaSession` + `AudioAttributes(USAGE_MEDIA,
  CONTENT_TYPE_SPEECH)` we already set are what AA needs to
  surface playback in its media stream; the explicit
  `setPreferredDevice` call was fighting against AA's audio
  policy. BT-only and wired-only setups (no AA) continue to
  prefer the personal output as before.
