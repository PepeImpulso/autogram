# v1.23.0-rc.9 — Pause now stops TTS 🤫

Pepe-reported on rc.8: the pause button doesn't actually silence
playback when what's playing is text-to-speech (i.e. a text message
in History, or an audio message whose summary is being read aloud
because `summarizeLongMessages` is on). The button toggled visually
to Play, but the voice kept speaking — and depending on what the
user did next, a new incoming audio could even start playing on top
of the still-going TTS.

## 🐛 Fixed

- **Playback · `pause()` now stops TTS too.** Pre-rc.9 `pause()`
  only touched `AudioPlayer.pause()`, which is a no-op when the
  active playback is the `TtsPlayer` engine. The `_playbackStatus`
  setter still flipped to `Paused`, so the row's button toggled to
  Play visually while the voice kept speaking — the user couldn't
  silence it. Now `pause()` checks `ttsPlayer.isSpeaking()` first;
  if true it routes through a new `TtsPlayer.cancel()` that stops
  the engine WITHOUT firing the pending `onDone` callback (so the
  autoplay-drain `speak()` callbacks don't auto-advance the queue
  under the user — they pressed pause for silence, not for "skip
  to next message"), nulls out `currentPlayingId`, marks the row
  `PLAYED` so it leaves the *Now Playing* panel, and flips the
  session to `STOPPED`. A re-tap on Play starts a fresh utterance
  from the beginning — the only sensible "resume" for TTS, which
  Android's `TextToSpeech` engine has no genuine pause/resume for.

  Affects two surfaces the user explicitly reported:
  - **History tab** · text-message row's play/pause button now
    actually pauses TTS instead of just toggling the icon.
  - **Pending tab** · the *Now Playing* panel's transport pause
    button now silences a TTS-driven playback (summary / text)
    instead of leaving it speaking under the toggled icon.

## 🔧 Internal

- **`TtsPlayer.cancel()`.** New companion to `stop()`. Both call
  `engine?.stop()`, but `cancel()` drops the pending `onDone`
  instead of invoking it. `stop()` stays the right call when an
  external caller wants the queue-progression callback to fire
  (e.g. `stopAll()` invoked because the user started a new
  recording — that path expects the TTS callback to chain
  `playNext()`). `pause()` is the only current consumer of
  `cancel()`.
