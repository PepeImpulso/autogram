# v1.19.0 — Deep-audit fixes across playback + AA renderer 🧹🔒

User asked for a thorough bug review across everything landed in
v1.17.x–v1.18.7 (Android Auto rewrite + voice shortcuts + double-
playback fix). A hostile audit turned up 11 real issues, all fixed
here. No user-visible behaviour changes beyond the bugs going away
— the AA home still looks identical, the tap-to-record flow is
unchanged. Stability-only release.

## 🐛 Fixed — playback (`PlayReplyUseCase` + `TtsPlayer`)

- **Deadlock in `playVoiceMessage` failure branch.** Recovery
  after a play failure called `playNext()` **inside**
  `playbackStartLock.withLock { ... }`, and `playNext()` re-
  enters `playVoiceMessage` / `playTextMessage`, which try to
  reacquire the same mutex. `kotlinx.coroutines.Mutex` is not
  reentrant → the coroutine hangs on the second `withLock`. Any
  audio that failed to play froze the queue forever. Fixed by
  dispatching `playNext()` onto `playbackScope.launch { ... }`
  so it runs outside the lock.
- **`playAllPending()` only played the first message.** The
  for-loop called `playVoiceMessage` on each queue item, but
  audio playback is asynchronous — by the second iteration
  `audioPlayer.isPlaying()` returned true and every remaining
  message got re-enqueued. Replaced with a single kickoff; the
  audio-completion → `playNext()` chain drains the rest.
- **TTS `stop()` silently lost the pending `onDone` callback**,
  stranding messages in `PLAYING` state forever. Android's
  `TextToSpeech.stop()` does NOT fire `onDone` on the
  interrupted utterance. Now we track the current `pendingOnDone`
  in a `@Volatile` field and invoke it manually when `stop()`
  runs before a new `speak()`.
- **`stopAll()` didn't stop TTS.** A summary TTS that was still
  speaking when the user started recording would feed into the
  mic as background noise. Added `ttsPlayer.stop()` alongside
  the existing `audioPlayer.stop()`.

## 🐛 Fixed — Android Auto renderer (`AutogramSurfaceRenderer`)

- **Unsynchronised `HashMap` photo cache.** `drawIfReady` ran on
  `Dispatchers.Default` and multiple flow emissions could race
  the same map. Switched to a bounded (max 12) access-ordered
  `LinkedHashMap` wrapped in `Collections.synchronizedMap`, so
  concurrent reads/writes are safe AND the cache can't grow
  unbounded as the user adds pinned conversations.
- **`requestRender()` burst → `Surface.lockCanvas` race.** 5
  upstream flows all call `requestRender()` on state change;
  each used to spawn its own `Dispatchers.Default` coroutine,
  and concurrent `lockCanvas` on the same Surface is
  undocumented-but-fragile. Replaced with a CONFLATED
  `Channel<Unit>` + single long-running worker so burst emits
  collapse into one frame.
- **Drawable rasterisation leaked 30+ bitmaps per frame.**
  `drawDrawableCentered` allocated a fresh Bitmap per glyph per
  call (mic + bolt + person × 10 avatars × N redraws/sec).
  Added a `ConcurrentHashMap<Long, Bitmap>` keyed on
  (resId, tint, sizePx) so the same rasterised glyph is reused
  across frames. Expected GC-pressure drop on lower-end AA
  head units.
- **Surface callback retained `CarContext` after screen destroy.**
  If AA skipped `onStop` before `onDestroy` (observed on
  reconnect), the renderer stayed registered with `AppManager`
  and kept the Screen instance alive. Now `onDestroy` calls
  `setSurfaceCallback(null)` defensively and invokes a new
  `AutogramSurfaceRenderer.dispose()` that closes the draw
  channel and clears both caches.

## 🐛 Fixed — `MainScreen`

- **One-frame flicker between `isRecording` flip and active
  target update.** Two separate flow collectors emitted in
  close succession; the renderer briefly saw
  `(isRecording=true, activeId=null)`. Merged into a single
  `combine(status, activeTargetId)` collector.
- **`onGetTemplate()` scheduled delayed coroutines as a side
  effect** for the Sent → Idle auto-reset. AA re-requests the
  template on visibility changes, so multiple resets would
  stack. Moved the 3-second reset into the state-flow
  collector; `onGetTemplate` is now pure.
- **Double-tap during recording spurious error**. Rapid second
  tap hit `IllegalStateException("No hay grabación en curso")`
  because `currentAudioFile` is nulled synchronously in
  `stopAndSend`. Added a synchronous `isRecording=false` flip
  in `onClick` so the second tap short-circuits before reaching
  the send use case.

## ⚠️ Known caveat not fixed here

The CarAppService manifest declares the `androidx.car.app.category.NAVIGATION`
category (needed for `NavigationTemplate` + `SurfaceCallback`).
AA's production host only grants the required signature-protected
permissions to apps on Gearhead's allowlist. Sideloaded Autogram
works because **"Unknown sources" is enabled in Android Auto →
Developer Settings** on the user's phone. A future public release
targeted at users who haven't enabled that toggle will either have
to (a) roll back to the v1.17.8 GridTemplate renderer or (b) ship
two CarAppService variants. Documented for posterity; no code
change in this release.
