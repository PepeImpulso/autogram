# v1.20.3 — Android Auto deep clean + audio routing rewrite + cross-cutting hardening 🚗🔊

This is the combined fix release for everything found across the
**13th–18th audit passes** (run jointly with the user's other agent).
The Android Auto symptom (app missing on the car screen, "no
messages received while driving" fallback) and the audio symptom
(music ducks but no replay audio in the car) get a second, more
forceful layer of fixes on top of v1.20.0/v1.20.2 since neither of
those landings turned out to be sufficient on real hardware.

A debugging note up front: the **Desktop Head Unit emulator is
broken with current Gearhead** (DHU is from March 2022; Gearhead
is 16.5 from late 2024). The DHU connects, completes the protocol
handoff, and then immediately drops the session with
`PROTOCOL_IO_ERROR(3) / READER_CLOSE(52)` before any app
discovery happens. So while every fix below targets the right
root cause according to the docs, the only verification path is
**testing on a real car**.

## 🐛 Fixed — Android Auto

### `automotive_app_desc.xml` is now `template`-only

v1.20.0 removed `MESSAGING` + `IOT` from the `CarAppService`
manifest categories. We left `<uses name="notification" />` in
`automotive_app_desc.xml` because the doc page says it's needed
for `CarAppExtender` notifications — but on Gearhead 16.5 that
descriptor capability *plus* an active CarAppExtender notification
can make the host route the user back to its own messaging
surface even with our service categorised as NAVIGATION. Dropping
it means Autogram declares only the templated experience, which
is what the AA launcher actually keys off. CarAppExtender
notifications still work — that's a per-`Notification` extender,
evaluated independently of the descriptor.

### `androidx.car.app: 1.4.0 → 1.7.0`

Newer Gearhead versions enforce stricter checks on older Car App
Library protocol versions. Bumping to 1.7.0 keeps us aligned
with what current Gearhead expects to negotiate.

## 🐛 Fixed — Audio routing in the car

### `USAGE_ASSISTANCE_NAVIGATION_GUIDANCE` when AA is connected

v1.20.0 stopped force-routing to BT A2DP when a car output type
was visible, but it still used `USAGE_MEDIA` for the audio
attributes. AA's audio policy treats USAGE_MEDIA differently from
nav-guidance audio — Maps and Waze use
`USAGE_ASSISTANCE_NAVIGATION_GUIDANCE` for their voice, and that
stream is what gets routed through the car's speaker channel
during a projection session. Audio attributes now switch to nav
guidance when a `TYPE_BUS / TYPE_USB_* / TYPE_HDMI*` output is
present, matching how every other working AA voice app does this.

### Explicit preferred-output route

`AudioPlayer.preferOutputRoute` now picks the output Android is
likely to use for these attributes (via
`AudioManager.getAudioDevicesForAttributes` on API 33+) and falls
back to a deterministic priority chain
(`TYPE_BUS → TYPE_USB_ACCESSORY → TYPE_USB_DEVICE → TYPE_HDMI*
→ TYPE_USB_HEADSET → TYPE_BLUETOOTH_A2DP → wired → BLE → SCO`).
The previous "let the OS decide" strategy still let some hosts
pick a paired-but-silent BT route on USB-AA sessions.

### `BLUETOOTH_CONNECT` is now requested at runtime

The permission was declared in the manifest but never asked at
runtime. On Android 12+ that meant `getDevices(GET_DEVICES_OUTPUTS)`
returned an incomplete list — exactly what made the audio-routing
logic blind to the car output device. `MainActivity` now requests
`POST_NOTIFICATIONS`, `BLUETOOTH_CONNECT`, and `READ_PHONE_STATE`
on first launch (one-shot — no re-prompt loop on every onResume).

## 🐛 Fixed — Cross-cutting

### TDLib database encryption — random per install, no forced relogin

The TDLib database was being opened with an empty encryption key
since the project's first commit. v1.20.3 generates a random
32-byte key on fresh installs and stores it in
`EncryptedSharedPreferences`. Existing installs with TDLib data
on disk keep using the empty key (legacy compatibility), so no
one is forced to re-pair their Telegram session.

### Pending playback queue actually gets restored on app start

`PlayReplyUseCase.restorePendingQueue` was being defined but never
called. The `pending_playbacks` table accumulated entries that
were forgotten on every cold start — turning the "play queued
replies after silent mode ends" feature into silent data loss.
Now wired from `AutogramApplication.onCreate`.

### `playAllPending` actually drains the queue

The queue drain re-checked `silentMode` / `autoPlayReplies` /
`isCallActive` for every item, so re-enqueuing was the most
common outcome. Added a `respectUserGates: Boolean = true`
parameter to `playVoiceMessage` / `playTextMessage` /
`playSummaryOrTranscription`; the queue drain calls them with
`false` so a previously-blocked message actually plays now that
the user's circumstances have changed.

### Suggestion chips no longer require an active recording

`MainViewModel.lastIncomingWithAudio` and the suggestion-chip
flow used to gate on `activeTargetId`, which is only set during
an in-flight send. Decoupled both — they now reflect the actual
most recent incoming voice / text regardless of recording state
(the v1.19.10 fix was for the "play last original" button; this
extends the same fix to the suggestion-chip pipeline).

### Photo decode hardening (everywhere)

- `ZoomablePhotoDialog`: sample-decoded to ~2 × screen width
  instead of full resolution. A 24 MP gallery photo would OOM
  the dialog on open before this.
- `AutogramSurfaceRenderer.loadPhotoBitmap`: same sample-decode
  applied to the AA surface renderer's avatar cache (previously
  pinning up to 100 MB per avatar in `photoCache`).
- `ManagePinnedViewModel.setPhoto`: SAF-picked photos are now
  sample-decoded + JPEG re-encoded (quality 85) at 1600 px long
  side instead of byte-copied verbatim. Settles under ~500 KB
  per circle photo, makes every downstream path (render, zoom,
  export-backup) faster and smaller.

### Backup integrity + import safety

- `ExportImportUseCase` removed the `SecretKeySpec.getDeclaredField("key")`
  reflection — Android 15 restricts hidden API access and the
  reflection would have started failing silently. Key bytes are
  now zeroised during `deriveKey` itself.
- `SettingsScreen.openDocumentLauncher`: pre-checks `statSize`
  on the picked URI (with a bounded read fallback) so a
  multi-gigabyte file picker target can't OOM the process before
  `ExportImportUseCase.import`'s 50 MB cap fires.
- `buildPhotosMap` skips photo files larger than 4 MB so a
  pre-fix legacy file can't single-handedly blow the backup
  budget.

### Other hardening from the same audit pass

- `LlmQuickReplySuggester` got the same 256 KB response-body cap
  that `LlmEndpointSummarizationEngine` already had.
- `CircleAvatar.colorFor` now uses `(hashCode and Int.MAX_VALUE)`
  instead of `abs(hashCode)` to dodge the
  `abs(Int.MIN_VALUE) == Int.MIN_VALUE` overflow.
- `AutogramTheme` switched from `view.context as Activity` to a
  safe `as?` so a non-Activity composable host doesn't crash.
- `PlayReplyUseCase.playbackScope` marked `@Volatile` (re-created
  in `stopAll`, accessed from MediaPlayer callback threads).
- `PlayReplyUseCase.restorePendingQueue` wraps the duplicate-check
  + add in a single synchronized block — `Collections.synchronizedList`
  doesn't cover iteration.
- QS-tile auto-record now handled in `MainActivity.onNewIntent`
  rather than a `LaunchedEffect` whose keys don't change between
  re-taps. Re-tapping the QS tile while Autogram is in the
  foreground actually triggers recording now.
- Sentry PII scrub extended to `event.exceptions[*].value` and
  `event.breadcrumbs[*].data` (was only scrubbing
  `event.message` before — TDLib error strings with chat ids
  bypassed the redactor).

### Lint cleanup

- Added `VIBRATE` permission to the manifest.
- `IncomingMessageNotifier` checks `POST_NOTIFICATIONS` permission
  before posting (replaces the silent `try { ... } catch (SecurityException) {}`).
- API 34 `setForeground` guard on the right SDK constant.

## ⚠️ DHU diagnostic note

If you try to test this with the Desktop Head Unit emulator
locally, you will likely see Gearhead drop the session with
`PROTOCOL_IO_ERROR / READER_CLOSE` and never render any app.
**This is a DHU-vs-Gearhead protocol mismatch, not a bug in
this release** — the DHU SDK package hasn't been updated by
Google since March 2022 and current Gearhead has moved on. The
only reliable verification path right now is **plugging the phone
into the actual car**.

## Install

Update from 1.20.2. No migration, no permission re-grant.

When you reconnect the car, look for Autogram under the
**Navigation** section of the AA launcher (where Waze / Google
Maps live), not under Messages. Tap-to-replay and the audio
playback through car speakers should both work; if the audio is
still inaudible while connected, the most likely remaining cause
is `BLUETOOTH_CONNECT` having been denied — open Autogram on
the phone, accept the Bluetooth permission prompt, and try
again.
