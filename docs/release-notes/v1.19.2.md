# v1.19.2 — Third audit pass: 9 bugs across update + TDLib + workers + security 🔐

Third hostile audit, this time focused on code paths the previous
two passes didn't cover: update flow, TDLib wrapper, background
workers, DI wiring, phone-side activities, import/export, and
manifest. Found 9 genuine bugs worth shipping. Stability + security
release; no new user-visible features.

## 🚨 Fixed — HIGH severity

### Foreground service type will fail on Android 14+

`MtprotoReceiverService` declared `foregroundServiceType="dataSync"`,
which the OS budgets to 6 hours per day on Android 14+ and will
increasingly tighten in future releases. Switched to
**`foregroundServiceType="specialUse"`** with a declared
`PROPERTY_SPECIAL_USE_FGS_SUBTYPE` describing our MTProto long-poll.
Also updated `startForeground()` to pass the explicit type (required
at API 34+). Added the matching `FOREGROUND_SERVICE_SPECIAL_USE`
permission. Without this the service would have hit
`ForegroundServiceStartNotAllowedException` silently and TDLib
would stop receiving in the background.

### `TdLibClient.send()` had no timeout

If TDLib was wedged (mid-reconnect, stale auth, bad socket),
callers awaited forever — including `OutboxRetryUseCase` running
on WorkManager's 10-minute budget. The worker would miss the
deadline and every queued message would land in
`PERMANENTLY_FAILED` on a transient outage. Now wraps `send()`
in `withTimeoutOrNull(60_000)` and synthesises a TDLib-style
Error response on timeout so callers can retry cleanly.

### `OutboxRetryUseCase` processed batches without re-checking auth

If TDLib lost auth mid-batch (tower handover, session timeout),
the next 40+ iterations each called `tdLibClient.send()` on a
disconnected client — now each times out at 60s, and the whole
batch could consume the entire worker budget, promoting every
row toward `PERMANENTLY_FAILED`. Now re-checks
`authState.value is Ready` between iterations and returns
`Outcome.RETRY` at the first auth drop.

### Biometric unlock was non-blocking

`MainActivity.onResume` fired the biometric prompt and
**continued straight through** to TDLib startup + foreground
service launch regardless of the result. An attacker picking
up the phone had ~2-3 seconds of visible Autogram UI (and any
incoming voice could auto-play aloud) before the prompt
resolved and `finish()` landed. Now uses a
`CompletableDeferred<Boolean>` so the coroutine actually awaits
the auth outcome; on failure we `finish()` before doing any
privileged work.

### Unbounded Room queries OOM-risked long-term users

`observeAll(conversationId)` and `observeAllAcrossConversations()`
returned every row of `messages` with no LIMIT. After months of
daily use a user can accumulate 10k+ rows, each carrying
kB-scale `transcription` / `summary` columns. Every incoming
message triggered a full-table scan on the UI Flow → Main
thread block + heap spike. Added `LIMIT 500` on both UI flows
and a new unbounded `getAll()` method for retention + stats,
which genuinely need every row.

## 🔒 Fixed — MEDIUM severity

### Update installer race: receiver registered AFTER enqueue

`UpdateInstaller.downloadAndInstall()` called `dm.enqueue()`
first, then registered the BroadcastReceiver. An ultra-fast
download (cached / tiny) could fire `ACTION_DOWNLOAD_COMPLETE`
before we were listening, leaving the UI stuck on "Downloading"
forever. Now registers the receiver first, then enqueues.

### Update installer silently failed on denied `REQUEST_INSTALL_PACKAGES`

`launchInstall()` fired the install `ACTION_VIEW` regardless of
whether the user had granted the install-unknown-apps permission.
When denied, the installer UI silently dropped the APK with no
error. Now pre-checks `packageManager.canRequestPackageInstalls()`
and emits a clear `InstallEvent.Failed` with a localised message
directing the user to Settings.

### ExportImport was not transactional

`applyPayload()` wiped all quick replies, then inserted the
backup's replies, then updated conversations — in four separate
operations. A crash or disk-full in the middle left the DB
half-overwritten (e.g. quick replies wiped with nothing
replaced). Wrapped the DB writes in `Room.withTransaction` via
a new `TransactionRunner` seam (kept unit-testable). Photo
files written before the DB transaction are rolled back on
transaction failure so the whole import is all-or-nothing.

### `OutboxRetry` could leave rows stuck in `SENDING`

Flipped a message to `SENDING` state BEFORE calling
`buildContent()`. If the row had no sendable content (orphan,
schema drift), `buildContent()` returned null and the code
marked `PERMANENTLY_FAILED` correctly — but if the process was
killed in the 50µs between the SENDING write and the
PERMANENTLY_FAILED write, the row stayed in SENDING forever
(invisible to future retry runs, which only scan QUEUED_OFFLINE
and FAILED). Now `buildContent()` is evaluated first.

### `RetryWorker` used `APPEND_OR_REPLACE` — wasted battery

When the user fired 5 voice messages offline in a row, each
`enqueueOnce()` call appended a NEW worker even though one
worker drains the entire outbox. 5 separate wakeups for zero
additional work. Now `ExistingWorkPolicy.KEEP`.

### `EXTRA_AUTO_RECORD` was trigger-able by any installed app

`MainActivity` is exported (LAUNCHER category) and read
`EXTRA_AUTO_RECORD` to start recording on launch without user
interaction. Any third-party app could
`Intent(component=MainActivity).putExtra(EXTRA_AUTO_RECORD,
true)` and silently trigger a mic session. Now verifies the
referrer package matches our own before honouring the extra;
external-caller intents have the extra stripped and logged.

## Install

Update from 1.19.1. Nothing user-visible changes — the app looks
identical, the AA home looks identical, the send/playback flows
behave identically. Under the hood, though, the app is
substantially more robust in long sessions, more secure at the
biometric and intent layers, and won't fall over on Android 14+.
