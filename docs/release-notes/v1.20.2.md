# v1.20.2 — Six audit passes, zero-new-bug floor 🧽🛡️

The user said "keep auditing until nothing new turns up, then ship
one combined release". Did six more passes (13th through 18th).
Ten real findings, ten fixes, all bundled here.

## 🐛 Fixed

### 1. `LlmQuickReplySuggester` — unbounded response body

Sibling `LlmEndpointSummarizationEngine` has a 256 KB read cap on
the OpenAI-style response; the quick-reply suggester didn't. A
misconfigured or hostile endpoint could stream gigabytes through
`response.body?.string()` and OOM the process. Matched the cap.

### 2. `CircleAvatar.colorFor` — `abs(MIN_VALUE)` edge case

`abs(conv.id.hashCode()) % palette.size` worked by accident with
today's 8-colour palette (because `Int.MIN_VALUE % 8 == 0`) but
would have crashed the next time someone resized the palette to a
non-power-of-2. Masked the sign bit explicitly so future edits
stay safe: `(hashCode and Int.MAX_VALUE) % palette.size`.

### 3. `AutogramTheme` — unsafe `view.context as Activity`

`SideEffect { (view.context as Activity).window … }` crashes with
`ClassCastException` when the composable is hosted under a
non-Activity context (Dialog, ContextThemeWrapper, etc.). Changed
to `view.context as? Activity ?: return@SideEffect`.

### 4. `PlayReplyUseCase.playbackScope` — missing `@Volatile`

The scope is recreated inside `stopAll()` after cancellation.
MediaPlayer completion callbacks fire on the player's internal
thread, so a callback that reads `playbackScope` concurrently
with a main-thread `stopAll` could see a stale pointer. Marked
`@Volatile`.

### 5. `ZoomablePhotoDialog` — full-resolution decode

The pinned-circle zoom dialog decoded the stored photo with
`BitmapFactory.decodeFile(path)` — no sampling. A 24 MP photo
(50-100 MB decoded ARGB_8888) could OOM the dialog open on
mid-range devices. Now sample-decodes to ~2 × screen width,
which still covers the 6× pinch-zoom ceiling comfortably.

### 6. `AutogramSurfaceRenderer` — full-resolution avatar decode

Same bug on the Android Auto home: each pinned avatar was
cached in `photoCache` at raw resolution. For 12 entries × up
to 100 MB each, Android Auto's memory-constrained head unit
could be pinning well north of a gigabyte. Added a two-pass
sampled decode keyed to the tile's render size.

### 7. Unbounded `readBytes()` on SAF import

The backup-import code path did
`contentResolver.openInputStream(uri)?.use { it.readBytes() }`
with no cap — if the user pointed the SAF picker at anything
large (video, archive, another app's file), we'd load the whole
thing into memory before `ExportImportUseCase.import` ever got
a chance to reject it. Added a pre-read `statSize` check +
a bounded manual-copy fallback (for URIs whose size is
unknown).

### 8. `setPhoto` copied user photos verbatim

`ManagePinnedViewModel.setPhoto` was doing an `InputStream.copyTo`
of the picked URI — so a 24 MP gallery photo stayed 8-12 MB on
disk under `filesDir/circle_photos/`, got re-decoded at full
resolution on every avatar render, and bloated every encrypted
backup by ~33 % after base64. Now sample-decodes + JPEG-
encodes at quality 85 with a 1600 px long side — visually
indistinguishable, files settle under ~500 KB, all downstream
paths (render, zoom dialog, export) get faster and smaller.

### 9. `PlayReplyUseCase.restorePendingQueue` — unsync iteration

`Collections.synchronizedList` guards individual ops but NOT
iteration. The duplicate-check `!pendingQueue.any { … }` ran
outside a synchronized block; a concurrent add on another
coroutine could trip `ConcurrentModificationException`. Wrapped
the check-and-add as one atomic block.

### 10. QS-tile auto-record — second tap did nothing

`handleAutoRecordIntent` used to live inside a
`LaunchedEffect(pinned, hasMicPermission)` in `MainScreen`. Its
keys don't change on a second Quick-Settings tile tap that
arrives via `onNewIntent`, so the effect wouldn't re-fire →
the intent extra sat there unprocessed. Moved the handler to
`MainActivity.handleAutoRecordIntent` and called it from
*both* `onCreate` and `onNewIntent`, so every re-tap is caught.

### Bonus: `ExportImportUseCase.buildPhotosMap` per-photo cap

Legacy photo files from pre-fix-8 installs can still be multi-MB.
Added a 4 MB per-photo ceiling: oversize legacy files are
skipped (with a warning) instead of being base64-encoded into
the backup. New photos from the compressed `setPhoto` path sit
comfortably below 4 MB.

## Install

Update from 1.20.1. No migration, no permission changes.

New behaviour you may notice:

- **First time you pick a new circle photo** under Manage
  Shortcuts, Autogram will JPEG-compress it to ~500 KB instead
  of copying the raw gallery file. Previously-picked photos stay
  as-is; re-pick to get the new pipeline.
- **Backup export** may be noticeably smaller if you had legacy
  large photo files pinned (they're skipped above 4 MB now).
- **Quick Settings tile** now reliably triggers voice recording
  even when Autogram is already in the foreground — previously
  a second tap was a no-op.
