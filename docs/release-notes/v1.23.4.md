# v1.23.4 — TTS-vs-voice overlap + missing-audio recovery 🎚️🩹

Two playback bugs Pepe surfaced after running v1.23.3 in real use.

## 🐛 Fixed

- **PlayReplyUseCase · `playVoiceMessage` no longer talks over an
  in-flight TTS.** While the app was reading a text reply aloud and a
  voice note arrived from another circle, the voice started playing
  on top of the TTS — two engines, one user. The busy-check at the
  top of `playVoiceMessage` only looked at `audioPlayer.isPlaying()`,
  whereas `playTextMessage` and `playSummaryOrTranscription` already
  guarded on `audioPlayer.isPlaying() OR ttsPlayer.isSpeaking()`.
  Brought the voice path into symmetry: when TTS is speaking, the
  arriving voice now enqueues, and `playNext()` picks it up after
  the TTS callback fires.

- **PlayReplyUseCase · missing-audio recovery instead of silent
  abort.** Sentry `dfd923f9…` (`release=autogram@1.23.3+112`,
  `os=Android 16`, `device=SM-S936B`) showed `playVoiceMessage`
  hitting "Archivo de audio no encontrado" and just returning. Most
  likely trigger: a queued voice message survives an app restart
  via the persistent pending-playback table while TDLib's cache
  was evicted, so the stored `audioFilePath` no longer resolves on
  disk. The silent return left the row in `RECEIVED`/`PLAYING`
  state and — when we were dispatched from `playNext()` — stalled
  the queue drain on the next item. The branch now logs at WARN
  (recoverable env condition, not a code bug), marks the row
  `FAILED` with `audioFilePath = null` so it stops being picked up
  by the replay button or `lastIncoming` flow, and calls
  `playNext()` when `respectUserGates=false` to keep the queue
  draining. Also translated the leftover Spanish log line to
  English to match the project's logging convention.
