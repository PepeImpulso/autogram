# v1.19.9 — "Play last original" actually works + deferred audio cleanup 🎧🔁

Two interlocked bugs that together broke the HeroHeader replay
button. Fixing both so tapping the headphones icon always plays
the most recent incoming voice — the user explicitly asked for
this.

## 🐛 Fixed

### Replay button did nothing after the message was played once

Root cause was in two places:

1. **`autoDeletePlayed` nuked the file on play completion.** The
   setting defaults to ON. When auto-play (or manual play) of an
   incoming voice finished, we nulled `audioFilePath` and
   `delete()`-d the file. Next tap on the replay button found
   `lastIncomingWithAudio == null` and did nothing. The user's
   words were "interrupted playback then pressing again plays
   nothing" — the underlying audio was literally gone.

2. **`lastIncomingWithAudio` was gated on `activeTargetId`.**
   `activeTargetId` is only set while a send is in flight; the
   moment a send completes (or if the user isn't recording at all)
   it clears to null, collapsing the query to null. So even if the
   file still existed, the button went dark after every finished
   interaction.

Fixed with two surgical changes:

**`PlayReplyUseCase.playVoiceMessage`** no longer deletes the
audio on `onCompletion`. Files survive playback. Deleted the
space-saving behaviour? No — just moved it.

**`MtprotoReceiverService.handleVoiceNote`** now runs deferred
cleanup when a NEW voice arrives on the same conversation: any
previously-PLAYED incoming voice on that conversation has its
file dropped and path nulled. The *current* message is always
preserved, which is the property the replay button needs. The
user's `autoDeletePlayed` setting still does what it says on the
tin (deletes played audios to save space), it just does it when
a newer message supersedes instead of eagerly on play-completion.

**`MainViewModel.lastIncomingWithAudio`** dropped its
`activeTargetId` filter. Now computes "most recent INCOMING voice
with a file, across all conversations". The replay button is a
global affordance — it should point at whatever the user last
heard from anyone, not at "what I'm currently recording a reply
to".

## 🧹 Ninth audit pass — additional safety

While verifying the above I did a ninth hostile audit sweep.
Found one latent edge case worth tightening:

- **`playManually` with an externally-deleted file** (user cleared
  cache, retention worker raced, etc.) was silently returning
  while leaving `audioFilePath` set, so `lastIncomingWithAudio`
  would keep pointing at a ghost row and the toggle would loop on
  "button enabled → tap → nothing" forever. Now nulls the stale
  path on detection so the UI picks the next-most-recent voice
  instead.

No other new bugs surfaced in the audit. The v1.19.7 + v1.19.8
changes around the HeroHeader toggle, shortcut send sounds, status
pill auto-dismiss, CSO min-hold, and shortcut show/hide all
behave as designed once this playback-storage fix lands.

## Install

Update from 1.19.8. The `autoDeletePlayed` setting behaviour is
slightly different — your most recent voice on each conversation
is now always preserved (never auto-deleted), and older played
voices get freed when a newer one arrives. Net effect: replay
always works, space savings arrive one message later than before.
If you already deleted audio files mid-ago they won't come back
(obviously), but the next incoming voice will lock in the new
policy.
