# v1.19.3 — Fourth audit: 2 v1.19.2 regressions + LLM hardening 🧹

Fourth hostile audit caught two genuine regressions from v1.19.2
plus two real robustness issues in the LLM summarization path. All
four fixed.

## 🐛 Fixed — v1.19.2 regressions

### Stats screen silently capped at last 500 messages

v1.19.2 added `LIMIT 500` to `observeAllAcrossConversations()` to
stop the UI flow from scanning the whole message table on every
insert. But `GetStatsUseCase.observe()` sat on top of that flow,
so `totalSent` / `totalReceived` / `totalFailed` counts on the
Stats screen were silently capped at "last 500 messages" instead
of lifetime totals. A power user who sent 2000 messages saw a
max count of 500.

Added **`GetStatsUseCase.getLifetimeStats()`** — a one-shot
suspend that uses the unbounded `messageRepository.getAll()`. The
Stats screen no longer needs live updates (the user isn't
watching stats tick in real time) so `StatsViewModel` now calls
it on init + on explicit refresh, storing the result in a
`MutableStateFlow<Stats?>`. The old `observe()` Flow method is
kept for backwards compatibility but deprecated via a KDoc note.

### RetryWorker could delay new messages up to 5 hours

v1.19.2 changed `ExistingWorkPolicy` from `APPEND_OR_REPLACE` to
`KEEP` to stop stacking workers. Correct intent, wrong policy:
if a worker was waiting on `BackoffPolicy.EXPONENTIAL` after a
failed attempt (backoff capped at 5 hours), a fresh
`QUEUED_OFFLINE` message enqueued after would **keep** the
stale backoff and wait up to 5 hours for retry. Immediate-retry
UX broken on flaky-network scenarios.

Switched to **`ExistingWorkPolicy.REPLACE`**:

- Dedup: only one worker ever scheduled at a time.
- Backoff reset: a fresh message kicks off a new 30-second
  backoff instead of inheriting the stale one.

Trade-off: REPLACE also cancels any worker currently draining
the outbox mid-run, which could leave a row stuck in
`MessageState.SENDING` (invisible to the outbox query). Fixed
proactively: **`OutboxRetryUseCase.runOnce()` now calls a new
`MessageDao.resetStuckSending()` on every worker startup**,
promoting any lingering SENDING rows back to QUEUED_OFFLINE
before the drain loop. New worker resumes from where the
cancelled one left off.

## 🐛 Fixed — LLM path robustness

### No overall call timeout

`LlmEndpointSummarizationEngine.summarize()` relied on the
shared OkHttp client's read/connect timeouts (each ~10s). A
dribbling endpoint (1 byte/sec, stalled streamer) would hold
the call coroutine forever. Added
**`withTimeoutOrNull(30_000)`** around the whole request/
response cycle.

### Response body was unbounded

`response.body?.string()` had no size cap — a hostile or
misconfigured endpoint could stream gigabytes and OOM the
process. Added a **256KB cap** via `source.request(...)` +
`source.buffer.readUtf8(...)`. A real chat-completions reply
is typically a few KB, so 256KB gives ~100× safety margin.

## Install

Update from 1.19.2. The Stats screen now shows true lifetime
counts again; retry worker reacts to new messages within 30s
regardless of prior backoff; LLM calls can no longer wedge the
app's coroutines.
