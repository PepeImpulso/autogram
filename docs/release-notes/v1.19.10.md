# v1.19.10 — Tenth audit: replay button survives a flood of outgoing messages 📤🎧

Tenth hostile audit pass on the whole codebase. Found one real
latent bug related to the v1.19.9 replay-button fix; everything
else checked out. Fixed the finding.

## 🐛 Fixed

### `lastIncomingWithAudio` could be starved by recent outgoing traffic

v1.19.9 tied the HeroHeader replay button to
`MessageRepository.observeAllAcrossConversations()`, filtered to
INCOMING voices. That flow is capped at the **500 most recent
rows** (LIMIT 500 in DAO, added in v1.19.2 for UI latency). A
power user sending text shortcuts in bursts can push the last
incoming voice off the window — the 501st row and older are
invisible to the flow — which silently disables the replay
button even though the file + DB row are still there.

Added a dedicated DAO query:

```sql
SELECT * FROM messages
WHERE direction = 'INCOMING'
  AND audioFilePath IS NOT NULL
  AND audioFilePath != ''
ORDER BY createdAt DESC
LIMIT 1
```

Plumbed through `MessageRepository.observeLatestIncomingVoice()`.
`MainViewModel.lastIncomingWithAudio` now uses this instead of
filtering the 500-row UI flow. O(log N) with the existing
`createdAt` index — cheap and correct regardless of how many
outgoing messages the user has sent since the last incoming.
