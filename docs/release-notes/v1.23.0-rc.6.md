# v1.23.0-rc.6 — Tap-to-seek + live timer + 2 s drain delay 🎚️

Quality-of-life improvements on the playback path. All three changes
land on the assistant pre-release branch on top of rc.5.

## ✨ Added

- **Now Playing waveform · Tap and drag to seek.** The waveform on the
  Pending Queue's Now Playing panel is now interactive: tap any point
  along it to jump playback to that position, or drag horizontally to
  scrub. The local position state updates immediately so the UI doesn't
  flicker back to the old position before MediaPlayer reports the new
  one. AA's progress bar and lock-screen scrubber get the same
  treatment via the new `ACTION_SEEK_TO` transport action +
  `MediaSessionCompat.Callback.onSeekTo` override; PlayReplyUseCase
  forwards both paths to `AudioPlayer.seekTo()` and re-publishes the
  resulting position to the session synchronously so AA doesn't briefly
  snap back before its next 1 s state refresh.

- **History + Pending row · Live `0:15 / 1:30` readout.** When a row
  is the active playback target, a live elapsed/total timer appears
  under the subtitle, in the theme primary color, polled at ~250 ms.
  Disappears when the row stops being the active target (pause counts
  as not-playing per Pepe's request — the readout is a cue that the
  audio is *moving*, not just that this is the most-recent message).
  Shared formatter (`formatDurationMs`) was promoted from
  PendingQueueScreen-private to `SharedMessageUi` so both screens use
  the same shape.

## 🐛 Fixed

- **Recording-vs-autoplay drain · 2 s beat after the mic releases.**
  Pre-rc.6, when an incoming message arrived while the user was
  recording a voice note, the message was correctly enqueued (won't
  play over an open mic — that gate's been there since v1.22.0), but
  `drainPendingIfAutoPlay` fired *immediately* after stopAndSend /
  cancelRecording / stopWithoutSending. The user's complaint:
  the queued message's audio stepped on the user's own context-switch
  — they'd just released the mic and the speaker was already playing
  someone else's reply. Now `drainPendingIfAutoPlay` waits 2 s, then
  re-evaluates its guards (recording started again? someone else
  kicked playback? autoplay toggled off?) before draining. Manual
  drain via the HeroHeader "Play N pending" / Pending Queue Play All
  button still drains instantly — they go through `playAllPending()`
  directly, not `drainPendingIfAutoPlay`.

- **`drainPendingIfAutoPlay` now also checks the recorder.** The pre-rc.6
  busy-check was `audioPlayer.isPlaying() || ttsPlayer.isSpeaking()`.
  If the user immediately started a new recording right after sending,
  the drain could begin and step on the new mic. Defensive belt + the
  2 s delay means we re-check after the wait too.
