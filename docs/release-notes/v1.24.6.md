# v1.24.6 — Share-log button works + voice-reply diagnostics 📝🔊

Diagnostic release. v1.24.5's voice-reply audio fix (matching TTS's
nav-prompt audio path) didn't resolve Pepe's "voice replies still
silent in the Seat Ateca" symptom, and the Settings → Share log file
button was showing "Logs unavailable" — which made it impossible to
see what the playback path was actually doing on the device. v1.24.6
unblocks the log capture and adds an entry-time log line in
`AudioPlayer.play()` so the next car repro will tell us where the
voice replies actually go.

## 🔧 Fixed

- **"Share log file" always showed "Logs unavailable".** The
  FileLoggingTree writes the rolling debug log to
  `cacheDir/autogram-logs/`, and the share button calls
  `FileProvider.getUriForFile()` to expose that file via
  `${applicationId}.fileprovider`. But the
  `xml/file_provider_paths.xml` config didn't include a
  `<cache-path>` entry for `autogram-logs/`, so the FileProvider
  threw `IllegalArgumentException` ("Failed to find configured
  root that contains …"). The exception was swallowed by a
  `runCatching{}.getOrNull()`, leaving the user with the toast and
  no file. v1.24.6 adds the missing `<cache-path>` entry — the
  share button now hands off a real Uri the system chooser can
  resolve.

## 🩺 Diagnostics

- **`AudioPlayer.play()` now logs entry up-front.** Pre-v1.24.6
  the only entry log fired AFTER `start()` succeeded, which made
  routing-silenced playback indistinguishable from "play() never
  reached" in the captured log file. v1.24.6 logs the file name,
  speed, focus mode, the `useNavigationUsage` flag, the chosen
  `AudioAttributes` (usage + content type), and the system's
  output-device snapshot the moment `play()` is called — so the
  next car repro tells us exactly what attributes the MediaPlayer
  saw and what sinks were visible to the OS.

## 🧪 Build status

- `:app:assembleRelease` green.

## Install

In-app updater. After updating: in the car, reproduce the "voice
reply doesn't play" symptom once, pull the phone out, open
Settings → Send bug report / Share log file, send the file. The
log will name the routed output type for the failing voice
playback (built-in speaker / BUS / USB / etc.) which is the missing
piece needed to pin down the actual root cause.

## Migration notes

No schema change. No behavioural change beyond the FileProvider fix
and the additional log lines.
