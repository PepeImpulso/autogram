# v1.20.17 — Pending pill cleanup, History tweaks, autoplay diagnostics

Three usability fixes from a round of testing on v1.20.16, plus
diagnostic logging for the open auto-play-replies queueing report.

## Changed

- **Pending-queue surface is now a single button.** The header used to
  render *both* a "%d pending messages" status pill and a "▶ N pending"
  action button when there were queued replies — the same number twice
  in the same row. The pill is gone; the action button is the single
  surface for the queued count. Also: the count word is now capitalized
  ("8 Pending") and the play icon is bumped from 18 dp to 22 dp so the
  affordance reads at a glance against the 40 dp headphones circle
  sitting next to it.
- **History sorts newest-first.** Messages used to render
  oldest-at-top, like a chat log; users had to scroll to the bottom to
  see the latest reply. Now the most recent message is at the top of
  the list. Day groups inherit the order — Today first, then Yesterday,
  then older.

## Added

- **Clear-conversation action in History.** The toolbar now has a sweep
  icon (visible only when the conversation has at least one message)
  that opens a confirmation dialog and, on confirm, wipes every
  message + voice file for the currently-viewed conversation. Cascading
  delete cleans up the matching `pending_playbacks` rows, and the
  in-memory pending-playback queue is reconciled so post-clear
  playback can't accidentally try to play a row that was just deleted.
  Telegram's server-side history is untouched; if a fresh reply
  arrives later, TDLib syncs it back.

## Internal

- **Gate-firing logs in PlayReplyUseCase.** `playVoiceMessage`,
  `playSummaryOrTranscription`, and `playTextMessage` now emit a
  Timber.i line every time they enqueue instead of playing, naming
  the exact gate that fired (in-call / autoPlayReplies=false / audio
  already playing / TTS already speaking). `playSummaryOrTranscription`
  also warns when it returns silently because summary, transcription,
  and textContent are all blank — the previous behaviour swallowed the
  message with no breadcrumb. These feed Sentry breadcrumbs so the next
  time a user reports "auto-play is on but messages still queue" we
  can see which check tripped without having to ask.
